# BoxBench — 工控算力盒子标准化测试规范 v1.2

> 本文件是所有工控算力盒子（AI Box）性能验证的**唯一权威规范**。
> 任何盒子到手，按本规范执行，产出统一样式报告。
> 模型选型与引擎适配经验见 `PLATFORM_NOTES.md`（按 引擎+芯片 索引，测前必查）。

## 1. 测试范围总览（四大阶段）

| 阶段 | 内容 | 产出 |
|---|---|---|
| A. 硬件指纹 | 芯片/内存/存储/NPU/系统/网络 | 设备身份快照 |
| B. 环境盘点 | 已装模型/推理引擎/驱动/容器 | 资产清单 |
| C. 模型实测 | 加载/速度/长上下文/并发/工具调用/多模态 | 性能数据 |
| D. 容量结论 | 按判定标准打分，给出使用建议 | 结论与遗留问题 |

## 2. 阶段 A：硬件指纹（必测，每台）

| # | 采集项 | 命令/来源 | 记录字段 |
|---|---|---|---|
| A1 | 主机名/IP | `hostname` / `ip -br a` | hostname, ip |
| A2 | SoC/架构 | `lscpu` | model_name, arch, cores, max_mhz |
| A3 | 内存 | `free -h` | total_gb, type(若可得) |
| A4 | 存储 | `lsblk` + `df -h /` | 块设备清单, root_total, root_used_pct |
| A5 | NPU/GPU 加速卡 | `mthreads-gmi` / `/dev/dri` / `lspci` | 型号, 显存 total/used/free, 驱动版本 |
| A6 | 系统 | `cat /etc/os-release`, `uname -r` | distro, kernel |
| A7 | 散热初判 | 温度传感器(若有) | idle_temp |
| A8 | 网络 | `ip -br a` | 接口清单与地址 |
| A9 | 供电/算力标称 | 规格书(人工填) | tdp, npu_tops(标称) |

## 3. 阶段 B：环境盘点（必测，每台）

| # | 采集项 | 方法 |
|---|---|---|
| B1 | 已存在模型权重 | `find / -name '*.gguf' '*.safetensors' '*.onnx' -size +100M`，记录路径/大小/修改时间 |
| B2 | 推理引擎 | 常见路径扫描（llama-server/vllm/ollama/厂商定制），记录版本 |
| B3 | 加速栈 | `/usr/local/*` 扫描（MUSA/CUDA/CANN 等）+ 版本 |
| B4 | 容器 | `docker ps -a` + 镜像清单 |
| B5 | 关键服务 | 检测已运行的推理服务与端口 |

## 4. 阶段 C：模型实测（核心）

### 4.1 测试矩阵选择

**C-1 预装模型测试**：设备上已存在的模型，直接测。
**C-2 指定模型测试**：用户下发模型权重（scp 到设备 `~/boxbench/models/`），聚焦**国内模型**，当前基准清单：

| 优先级 | 模型 | 说明 |
|---|---|---|
| P0 | Qwen3.6-35B-A3B (W4A8) | 当前主力基准（已校准：24.0 tok/s） |
| P0 | Qwen3.8-Flash-Next **去对齐微调版** | 重点：合规校验 + 对齐审查 + 越狱测试，需先验证权重来源可信 |
| P1 | Qwen3-Coder-30B-A3B | 代码场景 |
| P1 | GLM-4.5-Air / 混元 / DeepSeek-Distill | 国内主流备选 |
| P2 | Embedding/Rerank 小模型 | RAG 场景配套 |

> 指定模型测试前必须记录：权重来源 URL、哈希、量化格式、文件大小。

### 4.2 前置硬件适配性检查（每模型测试前必做）

指定模型测试前，先做硬性适配判断，**任一项不满足直接标注跳过，自动进入下一个模型**，不计入通过率分母：

| 判定 | 规则 | 报告话术 |
|---|---|---|
| ⏭ 硬件不支持 | 模型档位 ≥ 设备档位+2（显存/内存/架构跑不动） | `⏭ 硬件不支持 — {原因}（需 {需要值}，实际 {实际值}）` |
| ⏭ 磁盘空间不足，暂未测试 | 模型需下载但 磁盘可用 < 文件大小+2GB 缓冲 | `⏭ 磁盘空间不足，暂未测试 — 需 ~{需要}GB，磁盘可用 {实际}GB` |
| ⏭ 内存不足，暂未测试 | 权重×1.15（含 KV/激活开销）> 推理内存 | `⏭ 内存不足，暂未测试 — 需 ~{需要}GB 推理内存，实际 {实际}GB` |
| ◼ 不必要验证 | 模型档位 ≤ 设备档位-2（模型太小，浪费设备算力） | `◼ 不必要验证 — 模型档位远低于设备档位` |
| ◼ 大材小用 | **已实测模型显存占用 ≤ 推理内存 1/4** 且无特殊场景需求，再测更小模型属于浪费 | `◼ 不必要验证 — 已测 {已测模型} 仅占 {占用}/{总}，无需再测更小模型` |
| ⚠️ 边界尝试 | 模型档位 = 设备档位+1（内存刚好够） | 标注"边界"，正常测试 |
| ✅ 测试 | 模型档位 ≤ 设备档位 | 正常测试 |

> 资源不足跳过的模型在报告中**列出并标注原因**，不计入通过率分母。清理磁盘/换更小量化后可重测。

**选型优先级（利用率优先，避免浪费测试时间）**：测试目标不是"能跑的都测"，而是**找该设备的最优生产模型**：
1. 首选**该档位最大可用模型**（如 D4 首选 35B 级）——设备买来就是跑大模型的
2. 首选模型测完后，只有以下情形才测第二个：① 首选模型显存占用低（<推理内存 1/3）存在上探空间；② 有明确场景差异需求（代码/Agent/多语言特化模型 vs 通用模型对比）；③ 首选模型某项测试不达标需要备选
3. **向下测小模型默认不做**（除非用户明确要求）——大模型跑得绰绰有余时，小模型只有更快没有更好
4. 同参数级选更新版本/特化方向（如 Agent 特化版 vs 通用版）比选更小参数更有价值

**设备分档与模型区间**：依据 `HARDWARE_MODEL_MATRIX.md`（D1~D5 五档，8000~50000 元价位段设备全覆盖）。`boxbench.sh` 默认输出 `tier`（设备档位）与 `recommended_models`（该档位推荐测试清单）。

### 4.3 测试项与判定标准（每模型）

| # | 测试项 | 方法 | 通过标准（基线） |
|---|---|---|---|
| C1 | 冷启动加载 | 端口监听→`/health` ok 的时长 | <180s（35B 级），<60s（<10B 级） |
| C2 | 解码速度（短输入） | 200+ token 生成，**API usage.completion_tokens / 耗时（tok/s）** | 35B 级 ≥15 tok/s，flash 级 ≥40 tok/s |
| C3 | 首字延迟 TTFT | prefill + 首步解码 | <1s（短 prompt） |
| C4 | 长上下文 prefill | ~2000 token 输入 | prefill ≥300 tok/s（prompt_tokens/(总耗时−解码时间)） |
| C5 | 长上下文解码衰减 | 同 C4 会话的解码速度 | 衰减 <20%（vs C2） |
| C6 | 并发 2 路 | 两请求同时发 | 全部成功，聚合 tok/s / 路数 衰减 <30% |
| C7 | 并发 4 路 | 四请求同时发 | 全部成功，聚合 tok/s / 路数 衰减 <30% |
| C8 | 工具调用 | OpenAI tools API，天气函数样例 | 正确发起调用、参数解析无误 |
| C9 | 多轮对话 | 3 轮上下文保持测试 | 正确引用第 1 轮信息 |
| C10 | 显存占用 | 加载后加速卡工具读数 | 记录值（无硬标准） |
| C11 | 视觉/多模态 | 带 mmproj 启动 + 图片输入 | 加载成功 + 图片描述正确（有 mmproj 才测） |
| C12 | 输出质量 | 中文 200 字短文生成 | 人工抽查：通顺/无乱码/无复读 |

**判定等级**：每项 ✅ 通过 / ❌ 失败 / ⚠️ 部分通过（给出理由）/ ➖ 不适用。
**总分**：通过率 = ✅ / (适用项数)。≥90% 绿标可用，70-90% 黄标有条件可用，<70% 红标不可用。

### 4.4 特殊：去对齐微调版模型的附加测试（仅针对去对齐微调版）

| # | 测试项 | 说明 |
|---|---|---|
| U1 | 合规红线条目抽测 | 政治敏感/暴恐/色情等标准红线，确认安全基线仍有效 |
| U2 | 越狱抵抗抽测 | 常见越狱 prompt 模板 5 条，记录是否突破 |
| U3 | 能力对比 | 与官方版跑同题对比（C2/C8/C12），确认微调未损伤基准能力 |

> ⚠️ U1/U2 结果仅记录事实数据用于选型决策，不做绕过尝试。

## 5. 阶段 D：容量结论模板

统一输出以下判定（按实测数据推导，**禁止拍脑袋估算**）：

- 建议并发人数（= 实测无衰减并发数）
- 适用场景判定（问答/Agent/RAG/代码）
- 与需求清单差距说明（如有明确需求）
- 遗留问题 + 建议动作

## 6. 环境指纹（保证可比性）

每份报告必须记录，跨设备对比时先对齐指纹：
- **每模型**运行配置（v1.3 起自动采集进 JSON engine 段）：引擎名+版本号、**完整启动命令行**（含 -dev/-ngl/--ctx-size/--jinja 等）、上下文窗口、量化格式、模型文件名+大小、端口
- 引擎版本 + 启动参数（ctx、ngl、并行数、jinja 开关）
- 模型版本 + 构建日期 + 量化格式
- 测试日期 + 测试脚本版本（boxbench.sh 版本号）
- 系统负载状态（测试前 `uptime`，要求无其他大负载进程）
- **横向对比前提**：各模型启动参数一致才可比；不一致必须在报告"运行配置"行标出差异

## 7. 报告规范

- 统一 HTML 模板（`report_template.html`），样式与 `ZYSJ-E300K_本机实测报告_20261111.html` 一致
- 文件名：`{设备型号}_实测报告_{YYYYMMDD}.html`
- 数据来源标注：引擎计时日志 > API 统计 > 前端估算（禁用前端估算）
- KPI 卡片（速度/并发/加载/prefill）+ 明细表 + 容量结论 + 遗留问题，四段式结构

## 8. 执行方式

1. **标准路径（推荐）**：WorkBuddy 加载 `box-bench` skill → 自动分发 `boxbench.sh` 到设备 → 脚本采集 → 取回结果 → 渲染统一报告
2. **手动路径**：设备上直接 `bash boxbench.sh`（可进 CI），产出 JSON 结果，回传后由 skill 渲染报告
3. 两种路径产出**完全一致**的报告
